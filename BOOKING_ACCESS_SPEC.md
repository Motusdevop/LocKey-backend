# Booking Access Spec

## Цель
Добавить в backend продуктовый поток доступа по бронированию через сторонний CRM/booking-сервис.

## Бизнес-сценарий
1. Пользователь бронирует комнату во внешней CRM.
2. CRM отправляет запрос в backend LocKey.
3. Backend создает запись доступа для одного бронирования.
4. Для бронирования генерируется человекочитаемый токен.
5. Токен привязывается:
   - к одному замку
   - к одному интервалу бронирования
   - к одному бронированию
6. Пользователь добавляет этот токен в мобильное приложение.
7. Пользователь приходит на точку и открывает приложение.
8. Приложение отправляет запрос в backend на открытие.
9. Backend валидирует токен и, если все корректно, отправляет команду `open` замку через WebSocket.

## Основные правила

### Токен доступа
- Токен человекочитаемый.
- Токен хранится в приложении как строка.
- Токен многоразовый в пределах окна бронирования.
- Один booking соответствует одному замку.

### Временная логика
- Доступ разрешен в пределах окна бронирования.
- Нужен буфер на ранний вход.
- Текущая договоренность: разрешать открытие за `5` минут до начала бронирования.
- Позже можно добавить и буфер после окончания, но сейчас это не зафиксировано.

### Инфраструктура
- В качестве БД используется PostgreSQL.
- PostgreSQL поднимается в контейнере.

## Важное дополнение: код на замке
Помимо бронирования и токена пользователя, нужно учитывать динамический код, который backend отправляет на замок по WebSocket.

Этот код:
- показывается на экране замка
- дублируется в QR-коде как ссылка
- используется как часть online-потока на месте

Пример ссылки на экране замка:
`http://45.154.35.214/LocKey/open/{lock_id}?s=ABC123`

Это важно, потому что итоговый сценарий открытия должен учитывать не только валидность токена бронирования, но и актуальный код, показанный на конкретном замке в конкретный момент времени.

## Следствие для backend
В backend будет как минимум два связанных слоя проверки:

1. Проверка права доступа по бронированию:
   - токен существует
   - токен активен
   - токен привязан к нужному замку
   - текущее время попадает в допустимое окно бронирования с буфером

2. Проверка актуального кода замка:
   - код соответствует текущему временному окну
   - код относится к нужному замку
   - код совпадает с тем, что backend ожидает для текущего шага

Только после обеих проверок backend может отправлять `open` на замок.

## Минимальные сущности, которые понадобятся дальше
- `booking_access` или аналогичная таблица доступа по бронированию
- `lock_id` как идентификатор замка
- человекочитаемый `token`
- `valid_from`
- `valid_until`
- `external_booking_id`
- статус записи доступа

## Что пока не зафиксировано
- Нужно ли ограничение по числу открытий в пределах бронирования
- Нужен ли буфер после окончания бронирования
- Как именно авторизуется внешний CRM-сервис
- Нужен ли аудит всех попыток открытия
