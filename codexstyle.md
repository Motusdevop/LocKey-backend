# Code Style

## Цели
- Писать backend для `uv` + async `FastAPI` + `SQLAlchemy` + `PostgreSQL`.
- Следовать pragmatic FastAPI best practices без лишних слоев и преждевременных абстракций.
- Работать через TDD: сначала тест, потом минимальная реализация, потом рефакторинг.
- Комментарии писать редко и только по делу, на английском.
- Логи централизовать через `loguru`.
- Держать репозиторий чистым: без `__pycache__`, `.pytest_cache` и других временных артефактов.

## Базовые правила
- Использовать Python 3.12+.
- Предпочитать async-first подход во всех слоях, где есть I/O.
- Не смешивать HTTP, бизнес-логику и доступ к данным в одном модуле.
- Не тянуть CRM-логику и IoT-код в базовый скелет backend без явной задачи.
- Не добавлять лишние абстракции заранее.

## Структура
- `api`: routers, dependencies, HTTP boundary.
- `core`: settings, logging, shared application setup.
- `db`: database session manager and persistence wiring.
- `schemas`: request/response models.
- `services`: business logic that does not belong in routers.

## Зависимости
- Роуты могут зависеть от сервисов и схем.
- Сервисы не должны зависеть от FastAPI, если это не нужно для конкретной задачи.
- Конфиг, логирование и database setup должны оставаться в понятных отдельных модулях, а не размазываться по проекту.

## TDD
- Для каждой новой фичи сначала писать тест на ожидаемое поведение.
- Тесты должны быть deterministic и isolated.
- На каждую bugfix добавлять regression test.
- Не писать реализацию, которая проходит тесты случайно.

## Тесты
- Использовать `pytest`.
- Для async-кода использовать async-compatible fixtures и clients.
- Тесты на сервисы держать отдельно от HTTP и интеграционных тестов.
- Названия тестов должны описывать поведение, а не внутреннюю реализацию.

## FastAPI
- Роуты должны быть thin controllers.
- Валидацию входа держать на границе.
- Ответы описывать через Pydantic response models.
- Dependency injection использовать через функции-провайдеры.

## SQLAlchemy
- Использовать async SQLAlchemy API.
- ORM-модели и database wiring держать в `db`.
- Не смешивать ORM-модели, API schemas и сервисную логику в одном файле.
- Транзакции управлять явно.

## Logging
- Использовать `loguru` как единую точку логирования.
- Логи должны быть структурными и понятными.
- Не логировать секреты, токены и чувствительные payloads.
- Для ошибок добавлять контекст, достаточный для диагностики.

## Naming
- Имена должны быть короткими, точными и предметными.
- Классы именовать существительными, сервисы - по их роли.
- Файлы и модули держать в `snake_case`.
- Не использовать сокращения, если они не общеприняты в предметной области.

## Comments
- Комментарии использовать только там, где код не может объяснить решение сам.
- Комментарии писать на английском.
- Не дублировать очевидное.

## Formatting
- Придерживаться одного форматтера и одного линтера на проект.
- Не спорить с автоформатированием вручную.
- Не допускать длинных, трудно читаемых функций.

## Repository Hygiene
- Не коммитить `__pycache__`, `.pytest_cache`, `.ruff_cache`, `.mypy_cache` и аналогичные временные каталоги.
- После локальных прогонов тестов и инструментов проверять, что в рабочем дереве не осталось мусорных артефактов.
- Хранить структуру `backend/app` чистой: только исходники, тесты и осмысленные конфигурационные файлы.
